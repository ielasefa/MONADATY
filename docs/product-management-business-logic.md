# Product management: stock and search

Product Management now supports audited, atomic +/− adjustments of the same catalogue stock consumed by checkout. A unit means one catalogue item (including one pack when that item is sold as a pack). Retrying a lost response reuses an operation ID stored as the stock-history primary key, so it cannot deduct twice. Negative stock, fractional quantities, invalid operations and integer overflow are rejected. Existing warehouse allocations move in the same transaction; unallocated stock remains supported without inventing warehouse records.

Checkout still decrements at order creation. Cancellation/refund status transitions return stock once; reopening consumes it again and is refused if stock has sold out. Warehouse returns follow the original order movements, including repeated cancel/reopen cycles. Product locks use a consistent order. Warehouse absolute adjustments now apply a signed difference; transfers and purchase receipts commit atomically, and receipts cannot exceed ordered quantities. Variant warehouse movements continue to use their separate variant stock.

Saving product metadata preserves stock changed by another sale. An intentional absolute quantity edit requires the form's original stock baseline; a stale edit returns 409. Database image/metadata/history writes share a transaction, while file cleanup runs after commit. Legacy catalogue identifiers are accepted alongside UUIDs. Duplicating a product starts the draft at zero stock.

Search matches multiple terms across name, SKU, barcode, brand, slug, category and collection. French accents, punctuation, hyphens, package spacing and Arabic diacritics are normalized without installing a database extension. SQL values are parameterized; stock filters and stable pagination share a repeatable-read snapshot. URL updates use the installed Next.js history integration so typing and filter changes do not race server navigations. The list refreshes on focus and periodically while visible; errors expose a retry action instead of pretending the catalogue is empty.

Validation results and screenshots are stored in `visual-qa/product-management`. Database tests refuse to write outside the disposable QA clone. Test orders call the order service directly and send no emails. Original account/session, product selection and store data are retained; no production schema changes are required.

Validation passed: production build, lint and TypeScript; all 250 unit/integration tests across 32 files; 23 real PostgreSQL checks (including concurrent retries, final-unit competition, order status cycles and warehouse rollback); and 10 browser workflows. Browser verification covered French, English and Arabic at 360, 390, 768 and 1440 pixels, with three axe-core scans reporting no automated violations. No unexpected page errors were recorded. The intentional dropped-response test verified safe retry behavior.
